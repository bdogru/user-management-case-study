# User Management — Roadmap

The requirements come from the case-study brief, which is kept locally and not committed. The work
is split into two steps. Each step is planned in `plan/step-N.md` and ships as a short sequence of
PRs (`[Step X/N]`), reviewed by the reviewer agent and merged by the owner.

## Out of scope

Per the brief: authentication, authorisation, pagination, deployment, additional screens or
navigation. Docker Compose, an optional extension in the brief, is not planned.

## Requirements and where they are delivered

| Requirement from the brief | Delivered in |
|---|---|
| List, get, create, update and delete users through one REST controller | 1/1 |
| `id` generated by the system | 1/1 |
| `name` required, editable | 1/1 |
| `email` required, valid format, read-only after creation; enforced by the backend and tested | 1/1 |
| Input validation and meaningful HTTP status codes | 1/1 |
| Duplicate email shows a message in the UI | 1/1 (409) and 2/1 (error line) |
| Automated tests of the key behaviour | 1/1 |
| Database choice stated in the README | this PR |
| One screen with the list and the create, edit and delete actions; email read-only in edit mode | 2/1 |
| README with the commands to build and run | 1/2 (backend), 2/2 (frontend) |
| Optional: OpenAPI documentation | 1/1 |
| Optional: possible improvements (concurrent edits, further tests) | concurrent edits handled in 1/1 (optimistic locking); the rest in the README at 2/2 |

## Implementation Steps

### Step 1: Backend

> **Status: done** — 1/1 in PR #2 (backend and CI), 1/2 in PR #3 (end-to-end run and docs).
> [plan/step-1.md](plan/step-1.md)

**What**: Spring Boot REST API for users on H2: validation, one exception handler with problem
details, email immutability, a unique email, optimistic locking, generated OpenAPI. CI workflow.

**PRs**: 1/1 implementation and CI; 1/2 end-to-end run and documentation.

**Manual test**: the end-to-end plan in `plan/step-1.md` (curl against the running application).

**Tests**: HTTP-level tests through the controller against the real H2 database.

---

### Step 2: Frontend

> **Status: done** — 2/1 in PR #4 (screen and CI job), 2/2 in PR #5 (end-to-end run and docs).
> [plan/step-2.md](plan/step-2.md)

**What**: One Angular screen: the user table, one form for create and edit, one error line. CI
builds the frontend.

**PRs**: 2/1 implementation and CI job; 2/2 end-to-end run and documentation.

**Manual test**: the end-to-end plan in `plan/step-2.md` (in a browser, against the running backend).

**Tests**: none in the frontend; it is generated without tests and the brief assesses it for function
only. The behaviour it relies on is tested in the backend.
